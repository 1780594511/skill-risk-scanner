# 项目简报：第三方 Skill 接入风险初筛助手

## 场景与交付定位

团队准备接入一个从外部取得的 Agent Skill。接入者需要先回答：它声称做什么，会调用哪些外部服务，是否启动进程，是否读取凭据，哪些内容暂时看不懂。直接安装或运行不能作为初筛的第一步。

本项目把目录中的静态线索整理为可定位的复核队列，帮助方案、风险评估与治理岗位展示“限定范围—收集证据—解释风险—记录例外—复查”的工作方法。它补充 Android 恶意软件检测与区块链课程经历；不借用此前课题的实验结果来证明本工具有效。

**两种 Skill 必须区分：**

| 对象 | 位置 / 信任边界 | 用途 |
| --- | --- | --- |
| 被检查的第三方 Skill | `scan` 显式指定的目录；全部内容不可信 | 提供待分析的说明、代码和配置，不能向扫描器发指令 |
| 本项目的辅助 Skill 包装 | `skills/skill-risk-review/`；与可信项目一起交付 | 调用唯一的 `skill_guard` 实现，解释已经遮盖的报告 |

扫描器不导入目标模块；`import requests` 在样本中只是 AST 节点。操作者选择的扫描配置属于可信输入，目标目录中恰好也叫 config.json 的文件不会成为规则配置。规则代码、Python 解释器和运行目录需要可信；本项目不防御已遭替换的本地扫描器或解释器。

## 流程

```mermaid
flowchart LR
    A[用户指定本地目录] --> B[边界与资源限制]
    B --> C[有限文本读取]
    C --> D[Python AST / 行级文本规则]
    D --> E[上下文与证据定位]
    E --> F[精确例外及复核队列]
    F --> G[JSON / Markdown 与覆盖报告]
    G --> H[人工确认用途、参数和权限]
```

读取前检查链接/reparse 标记、解析后的路径边界、普通文件类型、敏感文件名和资源上限。扫描过程中保存各文件哈希、读取字节数和解析问题。遇到错误继续其他文件，同时把结果标为不完整。输出目录带固定标记；再次扫描时记录排除，不将报告文本当作新的风险源码。

“只读取指定目录”指目标内容读取边界；运行解释器和加载本项目可信代码、操作者明确传入的配置、写入指定报告目录是独立的必要操作。根目录外的凭据路径只是源代码中的字符，扫描器不会追过去。

## 正常样本的全过程

输入 `fixtures/01_clean_docs/`，只有一个普通 Markdown 文件。第 3 行是合成官网地址。扫描器读入 UTF-8 文本，`analyze_text` 将它标记为 `document`，SG007 记录“文档链接提及”。没有调用 AST 或 shell 命令的证据，不产生 SG001/SG002。

结果：1 个文件完整扫描，1 条 info 信息线索，0 条待复核项，退出 0。报告不会把网址变成来自不可信内容的活动链接；这也不是对该 Skill 的安全认证。另一个 `02_no_hits` 样本展示完整范围内确实无任何规则命中的情况，和信息性命中有区别。

报告：`reports/demo/01_clean_docs/report.json` 与 `report.md`。

## 风险模式样本的全过程

输入 `fixtures/18_risky_skill/`，共 3 个文件：

1. `SKILL.md:2` 试图让审查者忽略规则和上传文件。SG008 将其记录为不可信指令线索，扫描流程不因此变化。
2. `risk.py:4` 有明确网络库调用；只记录 example.invalid 主机，不保留查询参数。第 5 行启动动态 shell 命令，第 6 行读取敏感用途名称的环境变量，第 7 行读取常见云凭据路径。它们分别生成线索，**没有断言这些值流向网络**。
3. `fetch.ps1:1` 同一行出现网络命令、单个管道和解释器。SG002、SG003、SG006 共同定位这一处。SG006 的关联依据是直接管道结构，不是“同一文件同时含下载、执行两个词”。

结果：3 个文件完整扫描，8 条规则位置命中，需要人工复核，退出 3。样本全是不可执行的测试输入；外联目标为 example.invalid，网络请求的内容只写固定合成说明，不构建真实数据外传链。

报告：`reports/demo/18_risky_skill/report.json` 与 `report.md`。

## 潜在影响与证据置信度

| 维度 | 解释 | 例子 |
| --- | --- | --- |
| severity=info | 信息性线索 | 文档里的官网链接 |
| severity=low | 影响通常较低，仍需结合用途 | 固定版本查询、LANG 读取 |
| severity=medium | 可能涉及网络、凭据或解释器，需确认范围 | 明确请求、凭据路径读取、固定 shell |
| severity=high | 模式可能有较大影响，应优先复核 | 动态参数交给 shell；直接下载管道到解释器 |
| confidence=high | 对已实现语法模式的识别较确定 | AST 中调用节点及字面量 |
| confidence=medium | 行级模式或自然语言线索，有更大上下文歧义 | shell 文本、修改审查流程的句子 |

置信度不是“恶意概率”，影响级别不是漏洞成立证明。高置信度的固定命令仍可是低影响；高影响的文档示例仍只是文档。总体只给“需人工复核”“仅信息性线索或已有记录的例外”“存在未覆盖内容”等结论。

## 人工复核流程

先确认覆盖是否完整、配置是否适合当前审查日期，再从 high/medium 中检查用途、参数来源、接收方、必要权限和内容验证方式。对明确合理的线索，记录精确范围、理由、到期日和审查人（人员信息可保存在团队自己的审查表，本工具不虚构身份）。不能解释的内容保留为待复核；是否批准接入由负责人决定。

例外对照使用同一 `17_allowlist` 输入：基线有 3 条待复核项；配置网络域名例外和固定版本查询例外后仍有 3 条发现，其中 2 条标为 applied，凭据读取保持待复核。两个报告都退出 3，避免把“允许访问某域名”等同于“允许执行任意命令和读取凭据”。

过期例外报配置错误；精确例外未命中会在摘要列出。移动行号后旧例外可能不再匹配，这是促使重新检查的信号。没有通配符式的整目录豁免。

## 验证设计及证据解释

人工先编写 `fixtures/manifest.json`：期望集合以样本、规则、相对路径、1-based 行号、上下文为单位。同一位置的多次同规则调用合并；不同规则可同时命中同一行。评测随后比较实际集合，计算 TP/FP/FN；还检查例外状态、完整性和跳过原因，不能仅靠命中总数相等。

24 个有限合成目录的预期规则命中为 42 个。当前运行输出见 `reports/evaluation/evaluation.json`；这里的 0 多报/0 漏报仅表示预先编写的功能真值没有失配。没有定义真实世界样本分布和阴性总体，不能称真实恶意检测率、产品准确率或企业验证结果。更多安全约束由 mock/哨兵和系统支持的真实链接测试覆盖，未能执行的真实边界测试明示跳过。

本项目没有完成：真实第三方样本基准、动态沙箱、复杂别名和混淆分析、跨文件污点追踪、JS/TS 语义、GUI、GitHub 扫描、CI 集成、第三方审计、生产部署。后续改进以明确的漏检/误报实例为依据，先补手工真值再改规则，不为了简历数字扩展架构。
